ISSUE 1 — Hardcoded Admin Credentials in Source Code
============================================================
Severity: CRITICAL
File: backend/controllers/authController.js (lines 22-26)
Status: OPEN

Problem:
  const ADMIN_CREDENTIALS = {
    email: "sanjivani@admin.org.in",
    password: "Admin@123",
    id: "admin",
  };
  Admin login is checked against these hardcoded values on every
  request, not against the database. Any developer with source
  access knows the admin password.

Fix:
  1. Add a password field to backend/models/Admin.js (use bcrypt).
  2. In authController.js, remove ADMIN_CREDENTIALS. Instead
     query the Admin collection and use bcrypt.compare().
  3. Create a one-time seed script (backend/seedAdmin.js) to
     insert the initial admin user into MongoDB.
  4. Store the initial admin email/password in .env, not in code.

ISSUE 2 — Secrets Committed to Git (Even with .gitignore)
============================================================
Severity: CRITICAL
File: .env
Status: OPEN

Problem:
  The .env file contains live secrets:
    MONGO_URI      → contains DB username:password
    JWT_SECRET     → weak, predictable secret key
    GEMINI_API_KEY → live Google API key
  While .gitignore excludes .env, these values have already
  been exposed if the repo was ever pushed to a shared remote.

Fix:
  1. Rotate ALL secrets immediately:
     - MongoDB: change the password in Atlas.
     - Google Cloud: revoke the API key and generate a new one.
     - JWT_SECRET: use a cryptographically random 64-char string.
  2. Generate a strong JWT_SECRET:
       node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
  3. Create .env.example as a template (no real secrets) and
     commit it to the repo.
  4. Remove .env from git tracking (if it was ever tracked):
       git rm --cached .env

ISSUE 3 — No Rate Limiting on Auth Endpoints
============================================================
Severity: HIGH
File: backend/routes/auth.js
Status: OPEN

Problem:
  POST /api/auth/login and POST /api/auth/signup have no rate
  limiting, enabling brute-force password attacks.

Fix:
  1. Install express-rate-limit:
       npm install express-rate-limit
  2. Add rate limiting to auth routes:
       import rateLimit from "express-rate-limit";
       const authLimiter = rateLimit({
         windowMs: 15 * 60 * 1000,  // 15 minutes
         max: 10,                     // 10 attempts per window
         message: { message: "Too many attempts, try again later" },
         standardHeaders: true,
         legacyHeaders: false,
       });
       router.post("/login", authLimiter, login);
       router.post("/signup", authLimiter, signup);

ISSUE 5 — No Input Size Limits
============================================================
Severity: MEDIUM
File: server.js (line 40), resume upload (line 62-64)
Status: OPEN

Problem:
  express.json() has no limit — an attacker can send huge
  payloads to crash the server. Resume upload also has no
  file size limit.

Fix:
  1. Add limit to express.json():
       app.use(express.json({ limit: "10kb" }));
  2. Add multer limits for resume upload:
       const upload = multer({
         storage: multer.memoryStorage(),
         limits: { fileSize: 5 * 1024 * 1024 },  // 5MB
       });

ISSUE 7 — JWT Stored in localStorage (Frontend)
============================================================
Severity: MEDIUM
Status: OPEN (frontend storage pattern)

Problem:
  The frontend stores JWT tokens in localStorage, making them
  accessible to any JavaScript running on the page (XSS).

Fix (future enhancement):
  - Use httpOnly cookies instead of localStorage for the JWT.
  - Requires backend changes to set cookies:
      res.cookie("token", token, {
        httpOnly: true,
        secure: process.env.NODE_ENV === "production",
        sameSite: "strict",
        maxAge: 7 * 24 * 60 * 60 * 1000,
      });
  - Frontend: remove manual token handling from localStorage.

ISSUE 10 — Error Messages May Leak Internals
============================================================
Severity: MEDIUM
File: server.js (line 281-282, 339-340)
Status: OPEN

Problem:
  Some error responses send the raw error message to the client:
    res.status(500).json({ error: error.message })
  This may leak stack traces, file paths, or internal logic.

Fix:
  In production, never send error.message to the client. Log it
  server-side and return a generic message:
    if (process.env.NODE_ENV === "production") {
      res.status(500).json({ message: "Internal server error" });
    } else {
      res.status(500).json({ message: error.message });
    }

ISSUE 12 — Resume Base64 Data in MongoDB (No Encryption at Rest)
============================================================
Severity: MEDIUM
File: backend/models/User.js (field: resumeBase64)
Status: OPEN

Problem:
  Resume PDFs are stored as base64 strings in MongoDB. If the
  database is compromised, all resumes are readable. MongoDB
  connection uses TLS/SSL, but data is stored in plaintext.

Fix:
  1. Use mongoose-encryption or field-level encryption for
     sensitive fields (resumeBase64).
  2. Or store resumes in cloud storage (S3) and store only
     the URL in MongoDB.
